# dsh-wechat-suite v5.0

**一个大版本：QQ 接入为第二个平台 · 一个控制台管两边 · 管理台路径护栏。**

这一版把"只服务微信"的桥变成了**双平台桥**，并且让管理台真正能同时管住两条渠道。
顺带修掉了三个会让人误判的缺陷——它们共同的特征是：**数据其实都在，界面却告诉你没有**。

---

## 一、QQ 成为第二个平台（不是兄弟项目，也不是分支）

以前的桥只认微信：会话前缀写死 `wechat-`、记忆写死一个文件、网关只有一个。
现在多了 `src/qq/`（官方机器人 API v2 的客户端与鉴权）和 `src/platform/index.ts`
（**平台接缝**），节点不再直接依赖"微信"这个词。

### 每个平台各自拥有

| 东西 | 微信 | QQ |
|---|---|---|
| 会话命名空间 | `wechat-…` | `qq-…` |
| 长期记忆 | `$DSH_HOME/wechat-memory/MEMORY.md` | `$DSH_HOME/qq-memory/MEMORY.md` |
| 问题台账 | `$DSH_HOME/wechat-problems.log` | `$DSH_HOME/qq-problems.log` |
| 白名单 | `allowFrom`，或 `allowFromByPlatform.wechat` | `allowFromByPlatform.qq` |
| 网关 | iLink（微信） | QQ 开放平台（AppID + AppSecret） |

**两条渠道的对话永远不共用一段上下文，也不会互相镜像。** 这是刻意的：把两条渠道并进同一段
上下文会让"谁在跟我说话"变得不可判定，我们不做。

### 为什么这是一次重构而不是加个 if

节点里七处地方都在问"这条会话是不是我的"。每一处曾经都硬编码 `'wechat-'`——
只修一处、漏掉其余，桥会**静默地坏掉**：`/sessions` 空、`/use` 没反应、出站拒发、
审批全部被转交、管理台白屏。所以命名空间只在一处推导（`platformNamespace()`），
其余全部经由它。

---

## 二、一个控制台管两个平台

管理台支持 `--profiles wechat,qq`（旧的 `--profile <p>` 与默认 `web` 照旧可用），
同一个网址下用顶部的平台切换器切渠道。每个接口都接受 `?platform=`。

### 这一版修掉的三个"数据都在、界面说没有"

它们根因是同一个：**控制台拿"profile 名"当"平台 id"用**。

| 症状 | 修前找的是 | 修后找的是 |
|---|---|---|
| 会话列表永远是 0 段 | `web-*` | `wechat-*` |
| 长期记忆显示"还没有" | `web-memory/MEMORY.md` | `wechat-memory/MEMORY.md` |
| 问题台账永远是空的 | `web-problems.log` | `wechat-problems.log` |
| 控制台发的命令桥收不到（看着像"点了没反应"） | `web-admin/queue` | `wechat-admin/queue` |

名字与实际服务哪个平台是两件事：一个叫 `web` 的 profile 可能**根本没写 `platform`**，
于是节点按默认挂了微信、把所有东西都命名成 `wechat-…`。控制台现在从**每个 profile 自己的
配置**里读平台 id（与节点同一处规则），两边不可能再漂开。

## 三、安全：控制台再也走不出自己的目录

`?platform=` 以前不经任何校验就进了路径拼接：

```ts
function patchFor(p) { return join(dshHome(), 'profiles', p, 'cordis.patch.yml') }
function validPlatform(p) { return PROFILES.includes(p) }   // 定义了，但从没被调用
```

于是 `?platform=..`、`?platform=../..`、反斜杠写法都能穿出 `profiles/`，
把任意路径下的 `cordis.patch.yml` **读出来**（`/api/state`、`/api/reveal`）甚至**写进去**
（`POST /api/config`，而桥是热重载，写入即等于让插件重新加载那份 YAML）。

**修复**：名单字符集校验（非法 profile 名直接拒绝启动）+ 路径围栏 + 在一处收口校验，
未知平台一律 **4xx**。**回归测试**（`test/admin-platform-guard.test.ts`，真进程 + 真 HTTP）
断言：7 种穿越写法都必须被拒、不得泄露其它 profile 的内容、带穿越的写入不得改动任何文件、
启动参数非法必须拒绝启动。

> 教训也写进测试了：这个洞能溜过当时全部 290 条测试，是因为**管理台此前没有任何测试**。

## 四、修复

- **保存不再把 profile 写坏**：YAML 标量按字段 `kind` 判断是否加引号。QQ AppID 这类
  `"1234567890"` 以前会被当成数字裸写成 `qqAppId: 1234567890`，下次启动被 schema 拒绝
  （`expected string but got …`），而**保存当时看起来是成功的**。
- **改前端立刻生效**：`admin/index.html` 改为每次请求读盘。以前它是启动时读进内存的，
  于是"改了没反应"与"改动本身无效"从外面看完全一样——这个坑本项目反复踩过。
- **灯控不再有内置设备地址**（承接 v4.1 的破坏性变更）：`esp32BaseUrl` 未配置时明确报错并给出填法。

## 五、升级须知

1. **微信侧无需改配置**：没写 `platform` 的 profile 照旧服务微信，会话、记忆、台账路径都没变。
   **但请重启一次桥**，插件是进程启动时加载的。
2. **接 QQ 需要三样**：`platform: qq`（或 `platforms: [qq]`）、`qqAppId` + `qqClientSecret`
   （建议放 DSH 凭据 `QQ_BOT_APP_ID` / `QQ_BOT_CLIENT_SECRET`，而不是明文写在 profile 里）、
   以及 QQ 侧的 `allowFromByPlatform.qq`（填 QQ 的 `user_openid`）。
3. **一个 profile 服务一个平台**：要让两条渠道都上线，就起两个 profile（各挂各的网关）。
   它们可以共用同一个 `$DSH_HOME`，但别让两个实例同时抢同一个网关。
4. **管理台**：`node admin/server.ts --profiles wechat,qq --port 8790`，
   打开日志里打印的 `http://127.0.0.1:<port>/?token=…`。
   管理台**只监听 127.0.0.1**，并且要求本地回环 Host。
5. **没配 `allowFrom` 的 profile 起不来**（这是刻意的）：请把渠道 id 填进去。
   非白名单来客会被完全忽略、不进模型，并记一条台账——不确定自己的 id 时，
   先发一条，然后从台账里抄。

## 六、质量

- **294 条离线单元测试**全部通过（v4.1 为 261）。
- `tsc --noEmit` 零错误；`lib/` 与源码同步（有专门的守护测试）。
- 新增测试集中在最容易出事的地方：平台的隔离性（QQ 的会话/白名单/台账不会被微信认领）、
  QQ 网关的线格式与鉴权、管理台的路径护栏。

## 七、这一版没有的东西

- **不包含"合并模式"**：曾经尝试过让一个 profile 同时挂两个网关、共用一段上下文，
  该实现已被整块移除（它的状态机与事务化进入/退出过于复杂，且实测中曾导致宿主进入安全模式）。
  v5.0 的立场是：**两条渠道各自独立，绝不共用上下文。**
- **QQ 侧没有群聊/频道**：只做单聊网关所需的线格式，其余留了类型占位。
